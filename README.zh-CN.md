# Frontend Engine · 前端创作

[English](README.md) · **简体中文** · [日本語](README.ja.md) · [한국어](README.ko.md)

面向 Codex 的前端创作技能，将视觉方向、代码实现和结果验证衔接为一套工作流程。Frontend Engine 根据任务规模调整执行方式，覆盖局部界面修改、完整站点和复杂产品流程。

默认面向 Web。仅当用户明确要求 Apple 原生界面，或现有项目使用 SwiftUI 时，进入 SwiftUI 分支。

## 项目概述

Frontend Engine 为 AI 编程代理提供工作指令。它不是前端框架、组件库，也不是脱离 Codex 独立运行的应用生成器。

主要目标包括：

- 在需要视觉探索时，先确定能够指导实现的视觉目标。
- 沿用现有项目的框架、组件、设计 Tokens、数据契约和文件结构。
- 以满足需求的最小完整实现交付功能。
- 根据实际改动及其风险安排验证。
- 明确报告已实现内容、已执行检查和未验证事项。

适用于落地页、产品界面、响应式组件、界面重设计和明确指定的 SwiftUI 屏幕。孤立的逻辑修复与纯后端开发不属于本技能的主要范围。

## 安装

将本仓库克隆到 Codex 技能目录。默认位置为 `~/.codex/skills/frontend-engine`；设置了 `CODEX_HOME` 时，使用其下的 `skills/frontend-engine`。

### macOS 与 Linux

```bash
skill_root="${CODEX_HOME:-$HOME/.codex}/skills"
mkdir -p "$skill_root"
git clone https://github.com/AurvalLab/frontend-engine.git "$skill_root/frontend-engine"
```

### Windows PowerShell

```powershell
$codexRoot = if ($env:CODEX_HOME) { $env:CODEX_HOME } else { Join-Path $env:USERPROFILE '.codex' }
$skillRoot = Join-Path $codexRoot 'skills'
New-Item -ItemType Directory -Force -Path $skillRoot | Out-Null
git clone https://github.com/AurvalLab/frontend-engine.git (Join-Path $skillRoot 'frontend-engine')
```

确认 `SKILL.md` 直接位于安装后的 `frontend-engine` 目录内。若目标目录已存在且不是 Git 工作副本，应先备份，再手动同步技能文件，不要尝试覆盖克隆。

## 使用方法

通过 `$frontend-engine` 调用，并说明预期结果。可提供项目路径、目标页面或组件、参考资料、必要行为和验收标准。同时说明本次只做设计，还是需要完成实现。

### 探索新的视觉方向

```text
使用 $frontend-engine，为阅读 App 制作产品落地页。
主要行动是加入候补名单。先展示三个视觉方向，
等我选择后再开始实现。
```

### 实现已有参考

```text
使用 $frontend-engine，在现有 React 项目中实现这张截图。
复用已有组件和主题，适配不同屏幕，并将主要操作
接入现有注册流程。
```

### 完成局部修改

```text
使用 $frontend-engine，修复价格区块的移动端布局。
保留原有内容和桌面布局，检查受影响的断点与键盘交互。
```

### 指定单个阶段或原生界面

```text
使用 $frontend-engine，只做 Stage 1，输出蓝图，先不要实现。
```

```text
使用 $frontend-engine，在现有项目中制作 SwiftUI 设置页。
保留部署目标和状态模型，支持 Dynamic Type 和 Reduce Motion。
```

## 按任务规模调整流程

技能根据范围和风险选择执行方式。七阶段保留为明确的职责名称，不要求每项任务都经过七次用户审批。

| 任务 | 执行方式 | 文档记录 |
| --- | --- | --- |
| 局部调整 | 检查现有界面与受影响组件 → 修改 → 验证相关布局、状态和流程。 | 通常在交付回复中简述，或更新项目已有记录。 |
| 单页面或新组件 | 简要设计 → 实现与视觉打磨 → 验证；按需展开动效工作。 | 简要记录设计决定；后续交接需要时保存蓝图。 |
| 整站、复杂流程或大范围重设计 | 按依赖展开设计、Tokens、实现、打磨、动效和 QA 中适用的职责。 | 保存必要设计决定与验收证据，优先复用项目文档。 |

简单任务可以合并设计与 Tokens 决定、实现与视觉打磨，并在组件开发中完成基础过渡。复杂动效需要明确结构依赖和生命周期约定。静态任务不创建空动效规格或动画模块。

即使是小组件，涉及共享布局、复杂状态、安全或重要数据写入时，也需要扩大相应检查。简化流程不免除这些责任。

## 七阶段职责

| 阶段 | 职责 | 典型结果 |
| --- | --- | --- |
| 1 — Blueprint | 确定页面结构、内容、视觉方向、核心操作与必要状态。 | 设计决定或保存的蓝图。 |
| 2 — Tokens | 复用或定义当前任务需要的颜色、字号、间距和几何参数。 | 现有主题或 Tokens 定义的更新。 |
| 3 — Motion Spec | 说明复杂动效的触发、目标、结构依赖、清理与降级。 | 动效约定，必要时单独保存规格。 |
| 4 — Skeleton | 实现响应式结构、核心行为、必要状态和无障碍语义。 | 可运行的页面、组件或原生 View。 |
| 5 — Taste Polish | 依据选定方向打磨层级、字体、间距、素材和交互状态。 | 视觉完善的界面；按需记录复杂动效依赖。 |
| 6 — Motion | 实现约定动效，处理生命周期清理和减弱动态效果。 | 可用的动效与适当回退。 |
| 7 — QA | 检查实际输出、操作关键流程、修复缺陷并记录证据。 | 已验证的改动及明确的剩余限制。 |

单阶段请求停留在指定范围内。执行前结合当前项目检查必要上游决定；关键决定缺失时先解决，不默认为上游已经完成。

## 视觉探索与方案选择

新产品缺少明确视觉目标，或用户要求多个方案时，优先使用可用的 `product-design:ideate`。默认生成三张独立图片，等待用户选择后再实现；选中的图片及后续反馈共同构成实现目标。

已有截图、选定稿、Figma 参考、设计系统和现有界面代码可直接提供目标。局部修改不会自动触发新一轮风格探索。用户可以明确要求跳过视觉选择；仅要求尽快完成，不自动跳过已启用的选图流程。

无法使用 Product Design 时，可以先做简要文字设计再实现。用户明确要求图像，或命名的参考缺失时，应先解决缺口，不得假装已完成。SwiftUI 可复用适用的视觉探索，但原生实现始终按 SwiftUI 分支执行。

## 实现原则

- 优先复用项目组件与模式，再考虑新增抽象或依赖。
- 保留既有接口、校验、错误处理、数据行为和无障碍能力。
- 完成核心操作及必要的加载、空、错误、成功状态；不把占位内容当作真实接入。
- 从根因修复结构缺陷，更新受影响约定，并复查依赖行为。
- 核心内容的访问不依赖动画成功；按需处理减弱动态效果、初始化失败、取消、卸载与再次进入。
- 保持 SwiftUI 状态归属、View identity、部署目标和原生交互约定。

## 验证与交付

普通 Web 任务通常覆盖一个窄屏、一个桌面视口，以及受影响断点的两侧。整站和复杂响应式任务扩展到 320、375、768、1440、2560 CSS px 参考矩阵，并按项目实际支持范围调整。

检查相关视觉偏差、溢出、长内容、交互状态、键盘访问、表单、运行错误和动效回退。按需执行项目构建、类型与行为检查。性能结论需要测量依据，视觉上流畅不能直接证明达到某个帧率。

SwiftUI 验证依据实际支持的平台、窗口尺寸、文字缩放、外观和可用原生工具。浏览器模拟和模拟器不能证明真机行为。缺少必要工具时，对应项目明确列为未验证。

交付应说明：

- 改动内容，以及运行或预览方式。
- 实际检查的路由、组件、状态、尺寸和环境。
- 相关检查结果和已修复缺陷。
- 尚未解决的问题、未验证项及重要限制。

小任务可以用简短回复交代。复杂任务或需要交接的工作，应在项目已有文档或 `.agent-context/` 中保存必要记录。蓝图、动效规格和审计报告仅在内容有实际价值时保存，文件名映射到现有工程结构。

技能结构校验或本地构建通过，不能证明视觉验收、部署成功、生产就绪或真机兼容。
