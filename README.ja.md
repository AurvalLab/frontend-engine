# Frontend Engine

[English](README.md) · [简体中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

Codex 向けのフロントエンド制作スキルです。デザイン方針の決定から実装、検証までを一つのワークフローとして扱います。部分的な UI 修正からサイト全体の制作、複雑なプロダクトフローまで、作業範囲に応じて進め方を調整します。

既定の対象は Web です。Apple プラットフォームのネイティブ UI が明示的に求められている場合、または既存プロジェクトが SwiftUI を使用している場合は、SwiftUI 向けの手順を適用します。

## 概要

Frontend Engine は AI コーディングエージェントに作業指針を提供します。フロントエンドフレームワーク、コンポーネントライブラリ、Codex から独立して動作するアプリ生成ツールではありません。

主な目的は次のとおりです。

- デザインの検討が必要な場合に、実装の基準となるビジュアルを先に決める。
- 既存プロジェクトのフレームワーク、コンポーネント、デザイントークン、データ契約、ファイル構成を尊重する。
- 要求を満たすために必要な、最小限かつ完全な実装を届ける。
- 変更内容とそのリスクに応じた検証を行う。
- 実装内容、実施した確認、未検証事項を明確に報告する。

ランディングページ、プロダクト UI、レスポンシブコンポーネント、リデザイン、明示的に指定された SwiftUI 画面に適しています。単独のロジック修正やバックエンドのみの開発は、主な対象に含まれません。

## 必要な環境と任意の機能

| 機能・環境 | 必要になる場面 |
| --- | --- |
| ローカルスキルを利用できる Codex | スキルの指示を読み込み、使用するために必要です。 |
| Git | 以下の clone および更新コマンドに必要です。 |
| プロジェクトの既存ツールチェーン | 対象プロジェクトのビルド、型チェック、テストに使用します。新しいフレームワークは強制しません。 |
| Product Design と画像生成 | デザイン案の探索や、選択済みのビジュアルに基づく実装に利用する任意機能です。 |
| ブラウザーの自動操作・検査ツール | Web の実際の表示と操作を検証する場合に必要です。 |
| macOS と適切な Xcode ツール | SwiftUI のコンパイル、プレビュー、シミュレーター確認が必要または要求される場合に使用します。 |

これらの機能は実行環境から提供されます。このリポジトリをインストールしても、プラグイン、画像モデル、ブラウザーツール、アニメーションライブラリ、Xcode はインストールされません。

## インストール

Codex のスキルディレクトリに本リポジトリを clone してください。既定の配置先は `~/.codex/skills/frontend-engine` です。`CODEX_HOME` を設定している場合は、その配下の `skills/frontend-engine` を使用します。

### macOS / Linux

```bash
skill_root="${CODEX_HOME:-$HOME/.codex}/skills"
mkdir -p "$skill_root"
git clone https://github.com/AurvalLab/frontend-engine.git "$skill_root/frontend-engine"
```

### Windows PowerShell

```powershell
$codexRoot = if ($env:CODEX_HOME) { $env:CODEX_HOME } else { Join-Path $env:USERPROFILE '.codex' }
$skillRoot = Join-Path $codexRoot 'skills'
New-Item -ItemType Directory -Force -Path $skillRoot | Out-Null
git clone https://github.com/AurvalLab/frontend-engine.git (Join-Path $skillRoot 'frontend-engine')
```

インストール先の `frontend-engine` ディレクトリ直下に `SKILL.md` があることを確認してください。配置先が既に存在し、Git の作業コピーではない場合は、先にバックアップしてからスキルファイルを手動で同期してください。既存ディレクトリへの上書き clone は行わないでください。

## 使い方

`$frontend-engine` を指定し、期待する結果を説明します。可能であれば、プロジェクトの場所、対象ページやコンポーネント、参考資料、必要な動作、受け入れ基準を提示してください。デザインのみを行うのか、実装まで完了させるのかも指定します。

### 新しいデザイン方針を検討する

```text
$frontend-engine を使って、読書アプリのランディングページを制作してください。
主なアクションはウェイティングリストへの登録です。
実装前に異なるデザイン案を3つ提示し、私が選ぶまで待ってください。
```

### 既存の参考画像を実装する

```text
$frontend-engine を使い、このスクリーンショットを既存の React プロジェクトで実装してください。
既存のコンポーネントとテーマを再利用し、レスポンシブに対応させてください。
主要アクションは既存の登録フローに接続してください。
```

### 対象を限定して修正する

```text
$frontend-engine を使い、料金セクションのモバイルレイアウトを修正してください。
内容とデスクトップのレイアウトは維持し、影響するブレークポイントと
キーボード操作を確認してください。
```

### 単一ステージまたはネイティブ UI を指定する

```text
$frontend-engine の Stage 1 だけを実行してください。設計をまとめ、実装はしないでください。
```

```text
$frontend-engine を使い、既存プロジェクトに SwiftUI の設定画面を実装してください。
deployment target と状態モデルを維持し、Dynamic Type と Reduce Motion に対応してください。
```

## 作業規模に応じたワークフロー

スキルは範囲とリスクに応じて実行方法を選びます。7つのステージは役割の名称として維持されますが、すべての作業で7回の承認を求めるものではありません。

| 作業 | 進め方 | 記録 |
| --- | --- | --- |
| 部分的な修正 | 既存 UI と影響するコンポーネントを確認 → 修正 → 関連レイアウト、状態、フローを検証。 | 通常は簡潔な完了報告、または既存のプロジェクト記録を更新します。 |
| 単一ページ・コンポーネント | 簡潔な設計 → 実装と見た目の調整 → 検証。必要な場合に動きの設計・実装を追加します。 | 重要な設計判断を記録し、引き継ぎに役立つ場合は設計書を保存します。 |
| サイト全体・複雑なフロー・大規模なリデザイン | 設計、トークン、実装、調整、動き、QA のうち必要な役割を依存関係に沿って展開します。 | 必要な設計判断と検証結果を保存し、既存のプロジェクト文書を優先して再利用します。 |

小さな作業では、設計とトークンの決定、実装と見た目の調整をまとめられます。基本的なトランジションもコンポーネント開発中に実装できます。複雑なアニメーションでは、構造上の依存関係とライフサイクルの取り決めが必要です。静的な作業のために空のアニメーション仕様書やモジュールを作成することはありません。

小さなコンポーネントでも、共有レイアウト、複雑な状態、セキュリティ、重要なデータ書き込みに影響する場合は、検証範囲を広げます。工程を簡略化しても、これらの責任は省略しません。

## 7つのステージ

| ステージ | 役割 | 主な成果物 |
| --- | --- | --- |
| 1 — Blueprint | ページ構造、内容、デザイン方針、主要操作、必要な状態を決めます。 | 設計判断、または保存した設計書。 |
| 2 — Tokens | 必要な色、文字サイズ、余白、形状の値を再利用・定義します。 | 既存テーマやトークン定義の更新。 |
| 3 — Motion Spec | 複雑な動きのトリガー、対象、構造上の依存、クリーンアップ、代替動作を定義します。 | 動きに関する取り決め。必要に応じて仕様書を分離します。 |
| 4 — Skeleton | レスポンシブな構造、主要機能、必要な状態、アクセシビリティの意味構造を実装します。 | 動作するページ、コンポーネント、ネイティブ View。 |
| 5 — Taste Polish | 選定した方向に沿って階層、文字、余白、素材、操作状態を調整します。 | 見た目を整えた UI。必要に応じて複雑な動きの依存関係を記録します。 |
| 6 — Motion | 取り決めた動きを実装し、ライフサイクルの終了処理と視差効果を減らす設定に対応します。 | 動作するアニメーションと適切な代替動作。 |
| 7 — QA | 実際の出力と主要フローを確認し、不具合を修正して根拠を記録します。 | 検証済みの変更と、残る制限事項。 |

単一ステージの依頼は、その範囲内で実行します。前提となる設計判断は現在のプロジェクトと照合し、重要な判断が不足している場合は解決してから進めます。上流工程を完了済みと勝手に扱うことはありません。

## デザイン案の探索と選択

新しいプロダクトに明確なビジュアルの基準がない場合、または複数案を求められた場合は、利用可能な `product-design:ideate` を優先します。既定では独立した画像を3枚生成し、ユーザーが選ぶまで実装を開始しません。選択した画像とその後のフィードバックを実装の基準にします。

既存のスクリーンショット、選定済みのモックアップ、Figma、デザインシステム、既存 UI のコードが基準になる場合は、それを直接使用できます。部分修正で自動的に新しいスタイル探索を始めることはありません。ユーザーは案の選択を省略するよう明示的に指示できますが、単に「早く仕上げて」と依頼しただけでは、進行中の選択工程を省略しません。

Product Design が利用できない場合は、簡潔な文章による設計から実装へ進められます。画像が明示的に要求されている場合や、指定された参考資料が見つからない場合は、先に不足を解消します。完了したと見せかけることはありません。SwiftUI でも適切なデザイン検討は利用できますが、実装はネイティブ向けの手順に従います。

## 実装方針

- 新しい抽象化や依存関係を追加する前に、既存のコンポーネントとパターンを再利用します。
- 既存のインターフェース、検証、エラー処理、データの挙動、アクセシビリティを維持します。
- 主要操作と、必要な読み込み中・空・エラー・成功状態を実装します。仮の表示を実際の連携として扱いません。
- 構造上の不具合は原因から修正し、影響する取り決めを更新して関連する動作を再確認します。
- 重要な内容へのアクセスをアニメーションの成功に依存させません。必要に応じて動きを減らす設定、初期化失敗、キャンセル、アンマウント、再表示を処理します。
- SwiftUI の状態の所有関係、View identity、deployment target、ネイティブの操作慣習を維持します。

## 検証と成果物

通常の Web 作業では、狭い画面とデスクトップ画面、および影響するブレークポイントの前後を確認します。サイト全体や複雑なレスポンシブ対応では、320、375、768、1440、2560 CSS px を基準とする検証範囲に広げ、プロジェクトの対応範囲に合わせて調整します。

関連する見た目の差分、はみ出し、長い内容、操作状態、キーボードアクセス、フォーム、実行時エラー、アニメーションの代替動作を確認します。必要に応じてビルド、型チェック、動作テストを実行します。性能に関する主張には測定が必要であり、滑らかに見えるだけで特定のフレームレートを証明することはできません。

SwiftUI は、実際の対応プラットフォーム、ウィンドウサイズ、文字の拡大、外観、利用可能なネイティブツールに基づいて検証します。ブラウザーのエミュレーションやシミュレーターだけでは実機の動作を証明できません。必要なツールがない場合は、その項目を未検証として報告します。

成果物の報告には次を含めます。

- 変更内容と、実行・プレビュー方法。
- 確認したルート、コンポーネント、状態、サイズ、環境。
- 関連する検証結果と修正した不具合。
- 未解決の問題、未検証項目、重要な制限事項。

小さな作業は簡潔な報告で対応できます。複雑な作業や引き継ぎが必要な作業では、既存のプロジェクト文書または `.agent-context/` に必要な記録を保存します。設計書、アニメーション仕様書、監査レポートは内容に実用的な価値がある場合に保存し、ファイル名は既存の構成に合わせます。

スキルの構造検証やローカルビルドの成功は、見た目の受け入れ、デプロイ成功、本番利用への適合、実機互換性を保証しません。
