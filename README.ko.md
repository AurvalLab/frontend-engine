# Frontend Engine

[English](README.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · **한국어**

Codex용 프런트엔드 제작 스킬입니다. 시각적 방향 설정부터 구현과 검증까지 하나의 워크플로로 연결합니다. 특정 UI 수정부터 전체 사이트와 복잡한 제품 흐름까지, 작업 범위에 맞춰 진행 방식을 조정합니다.

기본 대상은 Web입니다. Apple 플랫폼의 네이티브 인터페이스를 명시적으로 요청하거나 기존 프로젝트가 SwiftUI를 사용하는 경우에는 SwiftUI 절차를 적용합니다.

## 개요

Frontend Engine은 AI 코딩 에이전트에 작업 지침을 제공합니다. 프런트엔드 프레임워크, 컴포넌트 라이브러리 또는 Codex와 별도로 실행되는 앱 생성 도구가 아닙니다.

주요 목표는 다음과 같습니다.

- 디자인 탐색이 필요한 경우 구현의 기준이 될 시각적 목표를 먼저 정합니다.
- 기존 프로젝트의 프레임워크, 컴포넌트, 디자인 토큰, 데이터 계약과 파일 구조를 존중합니다.
- 요청을 충족하는 최소한의 완전한 구현을 제공합니다.
- 실제 변경 사항과 위험에 맞춰 검증합니다.
- 구현한 내용, 수행한 확인, 검증하지 못한 항목을 명확히 보고합니다.

랜딩 페이지, 제품 인터페이스, 반응형 컴포넌트, 리디자인 및 명시적으로 요청한 SwiftUI 화면에 적합합니다. 개별 로직 수정이나 백엔드만 다루는 개발은 이 스킬의 주된 범위에 포함되지 않습니다.

## 요구 사항 및 선택 기능

| 기능 및 환경 | 필요한 경우 |
| --- | --- |
| 로컬 스킬을 지원하는 Codex | 스킬 지침을 불러오고 사용하기 위해 필요합니다. |
| Git | 아래의 복제 및 업데이트 명령에 필요합니다. |
| 프로젝트의 기존 도구 체인 | 해당 프로젝트의 빌드, 타입 검사와 테스트에 사용합니다. 새로운 프레임워크를 강제하지 않습니다. |
| Product Design 및 이미지 생성 | 시각적 탐색 또는 선택한 시각적 목표를 바탕으로 구현할 때 사용하는 선택 기능입니다. |
| 브라우저 자동화 또는 검사 도구 | 실제 Web 화면과 상호작용을 검증할 때 필요합니다. |
| macOS 및 적절한 Xcode 도구 | SwiftUI 컴파일, 미리 보기와 시뮬레이터 확인이 필요하거나 요청된 경우 사용합니다. |

이러한 기능은 실행 환경에서 제공합니다. 이 저장소를 설치해도 플러그인, 이미지 모델, 브라우저 도구, 애니메이션 라이브러리 또는 Xcode가 설치되지는 않습니다.

## 설치

Codex 스킬 디렉터리에 이 저장소를 복제합니다. 기본 위치는 `~/.codex/skills/frontend-engine`입니다. `CODEX_HOME`을 설정했다면 그 아래의 `skills/frontend-engine`을 사용합니다.

### macOS 및 Linux

```bash
skill_root="${CODEX_HOME:-$HOME/.codex}/skills"
mkdir -p "$skill_root"
git clone https://github.com/AurvalLab/frontend-engine.git "$skill_root/frontend-engine"
```

### Windows PowerShell

```powershell
$codexRoot = if ($env:CODEX_HOME) { $env:CODEX_HOME } else { Join-Path $env:USERPROFILE '.codex' }
$skillRoot = Join-Path $codexRoot 'skills'
New-Item -ItemType Directory -Force -Path $skillRoot | Out-Null
git clone https://github.com/AurvalLab/frontend-engine.git (Join-Path $skillRoot 'frontend-engine')
```

설치한 `frontend-engine` 디렉터리 바로 아래에 `SKILL.md`가 있는지 확인합니다. 대상 디렉터리가 이미 존재하고 Git 작업 사본이 아니라면, 먼저 백업한 뒤 스킬 파일을 수동으로 동기화합니다. 기존 디렉터리에 덮어쓰는 방식으로 복제하지 않습니다.

## 사용 방법

`$frontend-engine`을 지정하고 원하는 결과를 설명합니다. 가능하면 프로젝트 위치, 대상 페이지 또는 컴포넌트, 참고 자료, 필요한 동작과 인수 기준을 제공합니다. 디자인만 필요한지, 구현까지 완료해야 하는지도 명시합니다.

### 새로운 시각적 방향 탐색

```text
$frontend-engine을 사용해 독서 앱의 제품 랜딩 페이지를 제작해 주세요.
주요 행동은 대기 명단 등록입니다. 구현 전에 서로 다른 시각적 방향 3개를
보여 주고, 제가 선택할 때까지 기다려 주세요.
```

### 기존 참고 자료 구현

```text
$frontend-engine을 사용해 이 스크린샷을 기존 React 프로젝트에 구현해 주세요.
현재 컴포넌트와 테마를 재사용하고 반응형으로 구성해 주세요.
주요 행동은 기존 가입 흐름에 연결해 주세요.
```

### 특정 영역 수정

```text
$frontend-engine을 사용해 요금 섹션의 모바일 레이아웃을 수정해 주세요.
콘텐츠와 데스크톱 레이아웃을 유지하고, 영향을 받는 중단점과
키보드 상호작용을 확인해 주세요.
```

### 단일 단계 또는 네이티브 인터페이스 요청

```text
$frontend-engine의 Stage 1만 수행해 주세요. 설계안을 작성하고 구현은 하지 마세요.
```

```text
$frontend-engine을 사용해 기존 프로젝트에 SwiftUI 설정 화면을 구현해 주세요.
deployment target과 상태 모델을 유지하고 Dynamic Type과 Reduce Motion을 지원해 주세요.
```

## 작업 규모에 따른 워크플로

스킬은 범위와 위험에 따라 실행 경로를 선택합니다. 7단계는 명확한 역할 이름으로 유지되지만, 모든 작업에서 사용자 승인을 일곱 번 받아야 한다는 뜻은 아닙니다.

| 작업 | 실행 경로 | 문서화 |
| --- | --- | --- |
| 특정 영역 수정 | 기존 인터페이스와 관련 컴포넌트 확인 → 수정 → 관련 레이아웃, 상태와 흐름 검증. | 일반적으로 간단한 완료 보고 또는 기존 프로젝트 기록 업데이트로 충분합니다. |
| 단일 페이지 또는 컴포넌트 | 간단한 설계 → 구현과 시각적 다듬기 → 검증. 필요한 경우 모션 작업을 확장합니다. | 주요 설계 결정을 기록하고, 추후 인계에 도움이 될 때 설계안을 저장합니다. |
| 전체 사이트, 복잡한 흐름 또는 광범위한 리디자인 | 설계, 토큰, 구현, 다듬기, 모션과 QA 중 필요한 역할을 의존 관계에 따라 수행합니다. | 필요한 설계 결정과 검증 근거를 저장하고 기존 프로젝트 문서를 우선 재사용합니다. |

간단한 작업에서는 설계와 토큰 결정을 합치거나, 구현과 시각적 다듬기를 함께 진행할 수 있습니다. 기본 전환 효과도 컴포넌트 개발 중에 구현합니다. 복잡한 모션은 구조적 의존 관계와 생명 주기에 대한 명시적인 약속이 필요합니다. 정적인 작업에 빈 모션 명세나 애니메이션 모듈을 만들지 않습니다.

작은 컴포넌트라도 공유 레이아웃, 복잡한 상태, 보안 또는 중요한 데이터 쓰기에 영향을 준다면 검증 범위를 넓혀야 합니다. 절차를 간소화해도 이러한 책임은 생략하지 않습니다.

## 7단계 역할

| 단계 | 역할 | 일반적인 결과 |
| --- | --- | --- |
| 1 — Blueprint | 페이지 구조, 콘텐츠, 시각적 방향, 주요 행동과 필요한 상태를 정합니다. | 설계 결정 또는 저장된 설계안. |
| 2 — Tokens | 작업에 필요한 색상, 글자 크기, 간격과 형태 값을 재사용하거나 정의합니다. | 기존 테마 또는 토큰 정의의 업데이트. |
| 3 — Motion Spec | 복잡한 모션의 트리거, 대상, 구조적 의존 관계, 정리와 대체 동작을 정의합니다. | 모션 관련 약속. 필요하면 별도 명세로 저장합니다. |
| 4 — Skeleton | 반응형 구조, 핵심 동작, 필요한 상태와 접근성 시맨틱을 구현합니다. | 실행 가능한 페이지, 컴포넌트 또는 네이티브 View. |
| 5 — Taste Polish | 선택한 방향에 맞춰 계층, 타이포그래피, 간격, 에셋과 상호작용 상태를 다듬습니다. | 시각적으로 다듬은 인터페이스. 필요한 경우 복잡한 모션 의존 관계를 기록합니다. |
| 6 — Motion | 합의한 모션을 구현하고 생명 주기 정리와 동작 줄이기 설정을 지원합니다. | 동작하는 모션과 적절한 대체 동작. |
| 7 — QA | 실제 출력과 주요 흐름을 확인하고 결함을 수정하며 근거를 기록합니다. | 검증한 변경 사항과 명시적인 잔여 제한. |

단일 단계 요청은 지정된 범위 안에서 수행합니다. 필요한 선행 결정은 현재 프로젝트와 대조하며, 중요한 결정이 빠졌다면 먼저 해결합니다. 앞선 단계가 완료되었다고 임의로 가정하지 않습니다.

## 시각적 탐색과 선택

새 제품에 명확한 시각적 목표가 없거나 사용자가 여러 대안을 요청하면, 사용 가능한 `product-design:ideate`를 우선 활용합니다. 기본적으로 독립된 이미지 3개를 생성하고 사용자가 선택할 때까지 구현을 시작하지 않습니다. 선택한 이미지와 후속 피드백이 구현의 기준이 됩니다.

기존 스크린샷, 선택한 목업, Figma 참고 자료, 디자인 시스템과 기존 UI 코드는 직접적인 목표가 될 수 있습니다. 부분 수정 때문에 자동으로 새로운 스타일 탐색을 시작하지는 않습니다. 사용자는 시각적 선택을 생략하도록 명시할 수 있지만, 단순히 빠르게 끝내 달라는 요청만으로 진행 중인 선택 절차를 건너뛰지는 않습니다.

Product Design을 사용할 수 없다면 간단한 문서 설계 후 구현할 수 있습니다. 이미지를 명시적으로 요청했거나 지정한 참고 자료가 없다면, 해당 문제부터 해결해야 하며 완료한 것처럼 표현하지 않습니다. SwiftUI에서도 적절한 시각적 탐색을 활용할 수 있지만, 네이티브 구현은 SwiftUI 절차를 따릅니다.

## 구현 원칙

- 새로운 추상화나 의존 관계를 추가하기 전에 기존 컴포넌트와 패턴을 재사용합니다.
- 기존 인터페이스, 유효성 검사, 오류 처리, 데이터 동작과 접근성을 유지합니다.
- 핵심 행동과 필요한 로딩, 빈 화면, 오류, 성공 상태를 완성합니다. 자리 표시자를 실제 연동으로 표현하지 않습니다.
- 구조적 결함은 원인부터 수정하고, 관련 약속을 갱신한 뒤 의존하는 동작을 다시 확인합니다.
- 핵심 콘텐츠 접근을 애니메이션 성공에 의존시키지 않습니다. 필요한 경우 동작 줄이기, 초기화 실패, 취소, 언마운트와 재진입을 처리합니다.
- SwiftUI 상태 소유권, View identity, deployment target과 네이티브 상호작용 관례를 유지합니다.

## 검증과 전달

일반적인 Web 작업은 좁은 화면과 데스크톱 뷰포트, 그리고 영향을 받는 중단점 양쪽을 확인합니다. 전체 사이트와 복잡한 반응형 작업은 320, 375, 768, 1440, 2560 CSS px 기준 행렬로 범위를 넓히며, 프로젝트가 실제로 지원하는 범위에 맞춰 조정합니다.

관련 시각적 차이, 넘침, 긴 콘텐츠, 상호작용 상태, 키보드 접근, 폼, 실행 오류와 모션 대체 동작을 확인합니다. 필요에 따라 프로젝트 빌드, 타입 검사와 동작 테스트를 수행합니다. 성능을 주장하려면 측정 근거가 필요하며, 매끄럽게 보인다는 이유만으로 특정 프레임 속도를 입증할 수는 없습니다.

SwiftUI는 실제 지원 플랫폼, 창 크기, 텍스트 확대, 외관과 사용 가능한 네이티브 도구를 기준으로 확인합니다. 브라우저 에뮬레이션과 시뮬레이터만으로 실제 기기의 동작을 입증할 수는 없습니다. 필요한 도구가 없다면 해당 항목을 미검증으로 보고합니다.

결과 보고에는 다음이 포함되어야 합니다.

- 변경한 내용과 실행 또는 미리 보기 방법.
- 확인한 경로, 컴포넌트, 상태, 크기와 환경.
- 관련 검증 결과와 수정한 결함.
- 미해결 문제, 미검증 항목과 중요한 제한 사항.

작은 작업은 간단한 답변으로 설명할 수 있습니다. 복잡하거나 인계가 필요한 작업은 기존 프로젝트 문서 또는 `.agent-context/`에 필요한 기록을 남깁니다. 설계안, 모션 명세와 감사 보고서는 내용에 실질적인 가치가 있을 때 저장하며, 파일 이름은 기존 프로젝트 구조에 맞춥니다.

스킬 구조 검사나 로컬 빌드의 성공은 시각적 인수, 배포 성공, 프로덕션 준비 상태 또는 실제 기기 호환성을 입증하지 않습니다.
